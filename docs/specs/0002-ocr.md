# Run 0002: OCR (design-spec Phase 2, plus process isolation from Phase 3)

**Status:** signed off 2026-10-03 · **Date:** 2026-10-03 · **Lands on:** `main`
**Inputs:** `docs/design-spec.md` (cited as §n), `docs/specs/0001-text-path.md` (cited as 0001 §n, T-rows and D-rows by their ids), `docs/adr/` (cited as ADR n)

This document is the specification for the second spec-first implementation
run. It fixes the observable behaviour, the interfaces, the verification oracle
and the work-unit stack for everything the design spec calls Phase 2 — render a
page to grayscale, recognise it with Tesseract, return the result as a
`TextPage`, and run the per-document policy in `extract()` — together with
three additions the user decided: process isolation for OCR pulled forward from
Phase 3 (§7.6), both ways of linking Tesseract (vendored static build **and** a
`system-tesseract` feature), and the two open questions carried over from run
0001 (Q7, Q8). Fuzzing, sanitizers, `loom`, wheels and the SBOM stay in Phase 3.

Everything here was checked against the sources named in Appendix B (the
vendored fork as patched by run 0001, the `hayro` 0.7 rasteriser, Tesseract
5.5 and Leptonica 1.8 as published, PyO3 0.29.3) or probed black-box against
PyMuPDF 1.28.2 (Appendix A). Where the design spec was wrong or silent, this
document says so and decides. Facts that could not be verified are marked
**unverified** in place and listed in §7.

Requirement ids introduced here carry the prefix **O** (OCR run). Fork changes
continue run 0001's numbering at **H11**; patch files continue at `0020`.

## 1. Behavioural requirements

### 1.1 Rendering a page [§7.1, §10, R1, R4]

| ID | Requirement |
|---|---|
| O1 | `render_gray(page, dpi) -> GrayImage` rasterises one page at `dpi` dots per inch into an 8-bit luminance image whose dimensions are `ceil(w_pt × dpi / 72) × ceil(h_pt × dpi / 72)` for the page's visible box (CropBox ∩ MediaBox, 0001 T22) with `/Rotate` applied, so a page rotated 90° renders landscape. The background is opaque white; annotation appearance streams are drawn under the same filter as the text path (not hidden, not NoView, not `Popup`/`Link`; H8c). Luminance is `round(0.2126 R + 0.7152 G + 0.0722 B)` from the un-premultiplied RGBA pixmap after compositing over white. [§7.1 step 2] |
| O2 | The resolution actually used is `dpi' = min(dpi, floor(sqrt(max_render_pixels × 72² / (w_pt × h_pt))))`, never below 1. Lowering is silent except for the `TextPage.dpi` value, which reports `dpi'` (§10: "the resolution is lowered, not an error"). A page whose visible box is degenerate (zero or negative area, or over 14,400 pt a side after the PDF user-space limit) renders as a 1 × 1 white image rather than failing. |
| O3 | Rendering runs under the document's `Limits`: the interpreter budget (`max_ops_per_page`, `page_time_budget`, checked every 4,096 operators; H3) and the per-stream decode cap (H2b) apply unchanged because the renderer is a hayro `Device` driven by the same `interpret_page`. Exhaustion of either budget during rendering is `OcrPageError::Limit(kind)` and the page is **not** recognised (a partial raster would OCR garbage and the caller asked for a budget). Unlike the text device, the renderer runs Type 3 glyph procedures, tiling patterns and soft masks, so ADR 29's 50-level cap on those is load-bearing here and is re-tested on a 512 KiB stack in this run (§4.3). |
| O4 | Rendering decodes images (JPEG via zune-jpeg 0.5, JPEG 2000, JBIG2, CCITT, flate — all already in the lockfile for the text path, none with a thread pool). An image whose pixel count exceeds `max_image_pixels` (new `Limits` field, default 256,000,000 pixels; §10) is **not decoded** and is skipped with the warning `image: pixel limit` (`WarningKind::ImagePixelLimit`). The count checked is the declared `/Width × /Height` before any filter runs **and**, for the codecs that size their output from the encoded data rather than from the dictionary (CCITT, JBIG2, JPEG 2000; H13, Appendix B.4), the dimensions the codec reports from its header before it allocates — so the bound holds on the pixel buffers each decoder allocates, not only on what the image declares. An image that fails to decode is skipped with `image: decode failed` (`WarningKind::ImageDecodeFailure`, already defined, first raised in this run). Both are `TextPage` warnings on the OCR result, not errors. |
| O5 | The renderer's output depends only on the bytes, the options and the library version (C6): no threads, no SIMD-dependent arithmetic paths that differ between hosts (checked by the pixel-exact fixture test of §4.3 on both CI operating systems). |
| O6 | Nothing on the render path writes to file descriptors 1 or 2 (0001 T48 extended to rendering). |

`max_render_pixels` and `max_image_pixels` are the two memory bounds of
rendering: an A4 page at 300 dpi is 8.7 MP (8.7 MB gray, 35 MB RGBA during
rasterisation); the default 40 MP cap allows 300 dpi on pages up to about
56 × 76 cm and lowers larger pages.

### 1.2 The OCR engine [§7.2, §7.3, §7.4, D4, D5]

| ID | Requirement |
|---|---|
| O7 | `OcrEngine::tesseract(OcrConfig) -> Result<OcrEngine, OcrUnavailable>` validates the setup once, before any page: (1) resolve the tessdata directory (O9); (2) check that `<dir>/<lang>.traineddata` exists and is a readable regular file for every language; (3) create one Tesseract instance and `Init` it; (4) run one recognition over a built-in 1 × 1 white image to force model loading. Any failure is `OcrUnavailable { reason, tessdata, languages, searched, detail }` with `reason ∈ { NoTessdata, LanguageDataMissing, InitFailed, EngineNotBuilt }`. The instance from step 3 is kept as the pool's first member. |
| O8 | `OcrConfig` fields and defaults: `tessdata: Option<PathBuf>` (None), `languages: Vec<String>` (`["eng"]`; joined with `+` for Tesseract; each must match `^[A-Za-z0-9_]+$`, else `InitFailed` with a message naming it — a path separator or `..` in a language name must never reach the filesystem), `dpi: u32` (300; 1 ≤ dpi ≤ 2400), `max_instances: usize` (`min(available_parallelism(), 4)`, ≥ 1), `page_timeout: Duration` (60 s), `psm: PageSegMode` (Auto), `oem: EngineMode` (LstmOnly), `max_render_pixels: u64` (40,000,000), `isolation: Isolation` (`InProcess`; §1.5). Out-of-range values are rejected at construction with `OcrUnavailable { reason: InitFailed }` from Rust and `ValueError` from Python (an argument error, not a host condition). *Revised 2026-10-21 (internal #56 B10):* with `isolation = Process`, `max_render_pixels` above `MAX_PROCESS_RENDER_PIXELS` (66,977,776) is rejected the same way, because no raster above it fits one helper frame (O26). |
| O9 | Tessdata resolution, once per engine, in this order and with **no subprocess, shell or `PATH` search** (§7.3): (1) `OcrConfig.tessdata`; (2) `$TESSDATA_PREFIX`, accepting both `$P/<lang>.traineddata` and `$P/tessdata/<lang>.traineddata`; (3) the known directories, in order: `/usr/share/tesseract-ocr/5/tessdata`, `/usr/share/tesseract-ocr/4.00/tessdata`, `/usr/share/tesseract/tessdata`, `/usr/share/tessdata`, `/usr/local/share/tessdata`, `/opt/homebrew/share/tessdata`, **`/opt/local/share/tessdata`** (added: MacPorts, the development machine's layout; see D-3). A candidate is accepted when it is a directory containing `<first language>.traineddata`; the remaining languages are then checked against that directory only (a missing one is `LanguageDataMissing`, not a fall-through to the next directory, so the error names the directory that was chosen). `OcrEngine::tessdata()` returns the directory chosen. `searched` lists the candidates that were tried and **rejected**, in order; the one chosen is returned by `tessdata()` and is not in it (unit 08). An explicit `OcrConfig.tessdata` that lacks the first language's model is not an error by itself: resolution falls through to the next candidate, which is the literal reading of this row and of design-spec §7.3 (unit 08). |
| O10 | The pool is `Mutex<Vec<Instance>>` + `Condvar`, created lazily up to `max_instances`; a caller waits (no timeout: the running pages' own `page_timeout` bounds the wait) when all are busy. After each page the instance is `Clear()`ed and returned. An instance whose recognition returned an error, timed out, or whose shim reported a C++ exception is dropped, not returned; the next checkout creates a replacement (a failure to create it is `OcrUnavailable { reason: InitFailed }` raised from that `ocr()` call). |
| O11 | Fork safety (C7): the pool records the PID at creation. A checkout from a process with a different PID abandons the old pool — the instances are **leaked** (another thread of the parent may have been inside Tesseract at fork time, so freeing is unsafe) — and starts a fresh empty pool; the first page in the child pays one `Init`. Process-isolated pools (§1.5) additionally close their inherited pipe ends and respawn helpers. |
| O12 | `default_ocr_engine() -> Result<&'static OcrEngine, &'static OcrUnavailable>` (Rust) / `default_ocr_engine() -> OcrEngine` (Python, raising) builds one engine per process from `OcrConfig::default()` plus the environment (`TESSDATA_PREFIX`) on first use, under a `OnceLock`; a construction failure (an `Err`) is stored and re-raised on every later call without retrying (§7.2), while a **panic** inside the construction propagates to the caller (ADR 35) and leaves the `OnceLock` empty, so the next call constructs again. It is fork-aware through O11, not re-created in the child. |
| O13 | `OcrEngine::info() -> BackendInfo { name: "tesseract", version: String, languages: Vec<String>, tessdata: PathBuf, model_sha256: Vec<(String, [u8; 32])>, linkage: Vendored \| System, isolation }` (§14.2). The model checksums are computed once at construction (`eng.traineddata` is 4–23 MB; one read). |
| O14 | Process-wide Tesseract parameters are set once under a `Once` before the first `Init` and never changed: `debug_file` to the platform null device (`/dev/null`; `NUL` on Windows) so `tprintf` output never reaches stderr, and Leptonica's stderr handler is replaced by a no-op (O6 for the recognition path). Per-instance variables are passed to `Init` via the `vars_vec`/`vars_values` arrays, never through config files on disk. |
| O15 | Failure classification (§7.4, verified against `errors.py` as shipped): host-level → `OcrUnavailable` (Python `OcrUnavailableError`, the only `RuntimeError`); page-level → `OcrPageError::{Render(String), Recognition(String), Timeout(Duration), Limit(LimitKind)}` (Python `OcrPageError`, `OcrTimeoutError` for `Timeout`, `OcrPageError` carrying `limit_name` for `Limit`); closed → `OcrError::Closed` (Python `DocumentClosedError`). A recognition that runs and finds nothing is `Ok(TextPage)` with `text() == ""`. |

### 1.3 Recognition and the result [§7.1, F8, F9]

| ID | Requirement |
|---|---|
| O16 | `page.ocr(&engine, &OcrOptions { dpi })` performs O1–O2 with `dpi.unwrap_or(engine.config().dpi)`, then hands the gray image to one pooled instance with `SetImage(data, w, h, 1, w)`, `SetSourceResolution(dpi')`, the engine's `psm`, and `Recognize` under a monitor whose deadline is `page_timeout` from the start of **rendering** (the budget covers the whole call, so a slow render leaves less time for recognition). Tesseract's monitor is polled by Tesseract itself; when it reports a deadline, `Recognize` returns non-zero and the result is `OcrPageError::Timeout(page_timeout)`. |
| O17 | The result iterator is walked at `RIL_BLOCK` → `RIL_TEXTLINE` → `RIL_WORD`: each Tesseract block becomes a `Block`, each text line a `Line`, and the words of a line are joined with single U+0020 into the line's `Char`s (one `Char` per code point of the word's UTF-8 text, with the word's bounding box split evenly along the baseline direction — a word-level box, not glyph-level; `blocks()` stays `#[doc(hidden)]`). Lines and blocks appear in Tesseract's reading order. Empty words and lines are dropped, and so are words made only of space-like code points (*revised 2026-10-21*, internal #56 B8: U+0020, U+1680, U+3000 and U+FEFF, the text path's set, ADR 0048 — such a word would add spaces beside the joining U+0020 or leave a line of nothing but spaces). Coordinates are scaled from pixels back to page points (`× 72 / dpi'`) and flipped to PDF orientation (y up), so `Block::bbox()` has the same meaning for both sources. Each OCR line's box is the union of the engine's line box and its word boxes (unit 01). |
| O18 | `TextPage { source: TextSource::Ocr, dpi: Some(dpi') }`; `to_text()` has the same shape as the text path (0001 T33: every line ends `'\n'`, `BlankLine` adds one `'\n'` between blocks, an empty result is `""`). Text is sanitised exactly as the text path's is (0001 D-10: NUL, C0 other than TAB/LF/CR, U+FFFE/U+FFFF, unpaired surrogates → U+FFFD; Tesseract emits none of these in practice, but the invariant is enforced at one place for both sources). Word confidence is **not** exposed in this run. |
| O19 | The warnings of an OCR `TextPage` are the renderer's (O4, plus any hayro signal of 0001 §1.4 that fired during rendering); no warning kind is defined for recognition itself. |
| O20 | `OcrEngine` is `Send + Sync` (compile-time assertion); `Instance` is `Send` and not `Sync` and never escapes the crate. A page operation holds no engine lock while rendering, and no document lock while recognising (`Page::with_loaded` wraps the render only). |
| O21 | From Python, `Page.ocr(engine=None, *, dpi=None)` releases the GIL (`py.detach`) around rendering and recognition; `engine=None` uses `default_ocr_engine()`. `OcrEngine(...)` construction also detaches (model loading is tens to hundreds of milliseconds). |

### 1.4 The batch helper `extract()` [§12.4, C6, ADR 38]

| ID | Requirement |
|---|---|
| O22 | `Document::extract(&ExtractOptions) -> Result<Extraction, PageError>` (Rust) and `pdf_extract.extract(path, *, max_pages, min_chars=50, ocr=None, max_ocr_pages=500, workers=1, block_separator="newline", limits=None)` (Python; opens with `max_pages` and `limits`, then calls the method) run the policy of §12.4: (1) text pass over every page, `workers` scoped threads each taking a contiguous range of page indices (fonts are parsed once per worker only when H7 lands; this run creates one `InterpreterCache` per page as today, see §2.1); (2) a page is *sparse* when `text.trim().chars().count() < min_chars` — `trim()` is Unicode `char::is_whitespace`, matching Python's `str.strip()`, which is what the caller compares against today; (3) if `ocr` is given, the first `max_ocr_pages` sparse pages **in page order** are recognised, in parallel across `workers` threads (the engine's pool bounds Tesseract concurrency independently); (4) results in page order. |
| O23 | Per-page outcome (`PageResult { index, text, source, ocr_error }`): a text pass that fails with `PageError::Limit` yields `text = ""`, `source = Text`, `ocr_error = None` and the limit warning text in `Extraction.warnings` prefixed `page N: `; a non-empty OCR result is `source = Ocr`; an empty OCR result or an `OcrPageError` keeps the text layer with `source = TextFallback` and `ocr_error = Some(message)`; the first `OcrUnavailable` stops all further OCR for this document (sparse pages not yet started keep `TextFallback` with the unavailability message), and `ocr_status = Unavailable`; a sparse page beyond `max_ocr_pages` was never attempted and stays `source = Text` with `ocr_error = None`. `ocr_status` is otherwise `NotNeeded` (no sparse page or `ocr = None`), `Ok` (every attempted OCR succeeded), `Partial` (at least one `OcrPageError`), or `BudgetExhausted` (more sparse pages than `max_ocr_pages`; takes precedence over `Partial`). Unit 10 makes these exact: a limit hit in the text pass raises `WarningKind::PageLimit` (§3.3) and the page is not OCR'd (D-15); status precedence is `Unavailable` > `BudgetExhausted` > `Partial` > `Ok`; `workers = 0` is treated as 1 in Rust (a `ValueError` in Python); "empty" means empty after Unicode trim; whitespace-only OCR text is empty; `Extraction.warnings` is the document's warnings followed by the page-limit warnings. An empty OCR result is `TextFallback` with `ocr_error = None` (the oracle of §4.10 says so; the `Some(message)` above is for an `OcrPageError`) and counts as a success for `Ok`. |
| O24 | `extract()` is deterministic for given bytes, options and library version: the set of OCR'd pages depends only on page order and `min_chars`, never on which worker finished first (C6). With `workers = 1` no thread is created. Threads are `std::thread::scope` workers that join before the call returns (§8.5); a panic in a worker propagates after the scope (Rust) and becomes `InternalError` at the Python boundary. With `workers > 1`, after `Unavailable` the pages already in flight may still end as `Ocr`: which ones is timing-dependent, a documented exception to C6 (unit 10). |
| O25 | `extract()` honours `close()`: a document closed during the call makes remaining pages fail with `PageError::Closed`, which `extract()` returns as its `Err` (the partial result is discarded, as with any `Err`). |

### 1.5 Process isolation [§7.6, user decision 3]

| ID | Requirement |
|---|---|
| O26 | `OcrConfig.isolation = Isolation::Process` makes every pool slot a **helper process** instead of an in-process instance: `pdf-extract-ocr-helper`, one Tesseract instance per helper, talking over an anonymous pipe pair (stdin/stdout of the child; stderr is the null device). The public API, error classes and results are identical to `InProcess`; `TextPage`s are indistinguishable except for `OcrEngine::info().isolation`. The raster is bounded on the wire by `MAX_FRAME` (~67.1 MP), above `max_render_pixels`' default, so a raster larger than that fails under `Process` and succeeds `InProcess` only when `max_render_pixels` has been raised (unit 09). *Revised 2026-10-21 (internal #56 B10):* that asymmetry is gone. `OcrConfig::validate` refuses `max_render_pixels` above `MAX_PROCESS_RENDER_PIXELS` (66,977,776: `MAX_FRAME` less the `Recognize` header, one byte per pixel, less `RASTER_PIXEL_SLACK` for rounding) under `Process` at construction (`OcrUnavailable { InitFailed }`; `ValueError` from Python), so no page fails only under `Process`; the client still refuses an oversized raster before sending it, as a backstop. |
| O27 | A helper that exits, is killed, or sends a malformed frame while a page is in flight makes that page fail with `OcrPageError::Recognition("helper exited: <status>")`; the slot is marked dead, and the next checkout spawns a fresh helper (one spawn per failure, no retry of the failed page inside `ocr()`). A helper that exceeds `page_timeout` is killed (`SIGKILL`) and the page is `OcrPageError::Timeout`; the deadline is enforced by the parent, with the same monitor deadline also sent to the child so the common case ends cooperatively. A respawn's start-up (`Hello` → `HelloOk`) is allowed `max(page_timeout, 60 s) + 2 s` outside the page budget (§3.5; unit 09). *Added 2026-10-21 (internal #56 B11):* the helper's own warm-up recognition inside that start-up has a fixed 60 s budget (`WARMUP_BUDGET`), where an in-process instance warms up under `page_timeout`; the parent's wait for `HelloOk` is not bounded by it. |
| O28 | The helper is located at runtime, in order: `$PDF_EXTRACT_OCR_HELPER` (an absolute path to an executable regular file, as is `helper_dir`; a relative path is rejected with `OcrUnavailable { reason: EngineNotBuilt }` rather than searched); a file named `pdf-extract-ocr-helper` beside the loaded extension module (the Python package directory, which is where the wheel installs it — the binding passes `Path(__file__).parent` as `OcrConfig.helper_dir`); for Rust callers without `helper_dir`, a file of that name beside the current executable. Nothing on `PATH` is ever searched. A missing or non-executable helper is `OcrUnavailable { reason: EngineNotBuilt }` at engine construction (fail fast, O7), never at page time. |
| O29 | Engine construction with `Process` isolation spawns one helper and runs the O7 validation inside it (the parent does not load Tesseract at all; in-process and process modes never both initialise Tesseract in one process unless the caller builds both kinds of engine). The child receives `tessdata`, `languages`, `psm`, `oem` and the process-wide settings in the hello frame; it inherits no environment except `TESSDATA_PREFIX` (passed explicitly) and the locale variables. |
| O30 | Fork safety: a pool whose creator PID differs from the current PID (O11) closes its pipe file descriptors without waiting on the children (they belong to the parent) and respawns. Helpers are spawned with every descriptor above 2 closed explicitly in the pre-exec step (starting from fd 3; `Command` alone does not close inherited descriptors that lack `CLOEXEC`, unit 09) so a child never holds a document's file descriptor or another helper's pipe. |
| O31 | Test hook: the helper binary accepts the environment variable `PDF_EXTRACT_OCR_HELPER_FAULT` with values `abort-on-recognize` (calls `abort()` when the first `Recognize` frame arrives, imitating an `ASSERT_HOST`), `exit-on-recognize` (exits 3), `hang-on-recognize` (sleeps forever, for the parent-side deadline test), `garbage-on-recognize` (writes a frame with an invalid length prefix). The variable is read only by the helper, never by the library, and only when a second variable `PDF_EXTRACT_OCR_HELPER_FAULT_ARMED=1` is also set, so a stray value in a production environment cannot arm it. The in-process engine has the equivalent hook through `OcrEngine::with_backend` and a test `OcrBackend` (O33). The library forwards the `PDF_EXTRACT_OCR_HELPER_FAULT*` variables to the helper itself (it reads them), rather than the helper inheriting them (unit 09). |

## 2. Non-goals and bounded claims

### 2.1 Out of this run

- **Merging** an OCR result with a page's text layer; `extract()` picks one source per page (§12.4), as the caller does today.

- **Wheels, abi3, manylinux images, the SBOM, fuzzing, sanitizers (TSan/ASan), `loom`** — Phase 3. The process-isolation helper is built and tested in this run as a workspace binary; its *packaging* into the wheel is specified (§3.7) and exercised by `maturin develop` in CI, while the release-wheel matrix itself stays Phase 3.

- **`max_document_decoded_bytes`** (0001 D-11), **`mmap`** (0001 D-20), passwords, structured output.
- **Upstream pull requests** for H11/H12: patches are exported, not sent (0001 §2.1).
- **Corpus A (private documents)**: the OCR run against private scans is a documented script the user runs (§3.8), never CI.
- **Tuning Tesseract** (page segmentation modes beyond the default `Auto`, user words, pattern files, `tessedit_char_whitelist`): `psm` and `oem` are configurable; no other variable is exposed or tested.
- **Deskew, binarisation or denoising of our own** before recognition: the gray image goes to Tesseract as rendered; Tesseract's own Otsu thresholding is what runs. The noise/skew/blur variants of corpus D measure this, they do not gate a preprocessing step that does not exist.

### 2.3 What R1 means in this run

R1 ("no input may crash the process") is bounded, for OCR, to:

1. **Panics** anywhere in the Rust render path are caught at the Python boundary (O39). The hostile fixture set of 0001 Appendix C is run through `render_gray` at 36 dpi in Rust on a 512 KiB thread stack and through `Page.ocr` with a `ScriptedBackend` from Python.
2. **Stack depth** during rendering is bounded by hayro's 50-level nesting cap, which ADR 29 extended to Type 3 glyphs, tiling patterns and soft masks precisely because the renderer runs them; §4.3 proves each of the three self-recursive kinds at 50 levels on a 512 KiB stack **with the renderer**, which run 0001 could only do with the text device.
3. **Time** is bounded per page by `page_time_budget` for rendering (between operators) and by `page_timeout` for the whole `ocr()` call (Tesseract's monitor, polled by Tesseract between its own work units; in process mode additionally by the parent's `poll` deadline). One image decode or one Tesseract pass over a line is not interruptible.
4. **Memory** is bounded by `max_render_pixels` (pixmap), `max_image_pixels` (one decoded image's output and conversion buffers; the codec-internal residuals named in §2.2 excepted), the per-stream decode cap, and `max_instances` × (model + working set).
5. **Process termination by Tesseract** (`ASSERT_HOST`, `abort()`) is **not** prevented in `InProcess` mode and **is contained** in `Process` mode: the helper dies, the page fails, the parent continues (tested by the injected abort, O31). This is the one place where the run's claim depends on the configuration the caller chose; the default stays `InProcess` to match the design spec's choice (§7.6) and PyMuPDF's exposure — see Q1 in §7 for the alternative.

### 2.4 Robustness residuals (not defended in this run)

- **`unsafe` in the render graph**: pic-scale (hand-written NEON/SSE/AVX resampling kernels, ≈1,350 `unsafe` occurrences), moxcms (ICC transforms), peniko/color (small), PyO3. Not audited. hayro, vello_cpu, vello_common and png are `forbid(unsafe_code)`.
- **Cross-host pixel differences**: vello_cpu selects its SIMD level at runtime (`Level::new()`) and pic-scale dispatches to NEON or AVX kernels, so a rendered pixmap may differ by a gray level or two between an arm64 Mac and an x86-64 Linux host. Determinism is claimed **per host** (same bytes, same host → same pixels); cross-host agreement is gated with a tolerance (§4.3), not exactly. OCR text is compared by error rate (§1.6), never by pixel or byte equality.
- **Non-interruptible single operations** now include image decoding (JBIG2 generic-region decoding of a 256 MP image can take seconds), vello's final compositing of the pixmap, and Tesseract's work between monitor polls.
- **Tesseract's own memory**: the LSTM engine allocates per line proportionally to image width and model size; no cap of ours applies.
- **Leptonica and Tesseract `stderr`**: silenced through `debug_file` and Leptonica's stderr handler (O14); any message that bypasses both (a direct `fprintf(stderr, …)` in a code path we did not exercise) would break O40. The fd-level test covers the paths this run exercises, not every path in a 150k-line C++ library.
- **Helper process lifetime**: a parent killed with `SIGKILL` leaves helpers blocked on a closed pipe; they exit on `EOF`/`EPIPE` at the next read or write, which is immediate for an idle helper and at the end of the current page for a busy one. Helpers are not reparented to a supervisor and not cleaned up by any mechanism other than pipe closure.
- **`fork()` while a helper is mid-page**: the child's pool is abandoned (O30) and the parent's helper finishes the parent's page; the pipe is shared until the child's `close`, and a child that *wrote* to it before closing could corrupt the parent's stream. The child never writes (it closes first), but a signal arriving between `fork` and `close` is a theoretical window.
- **Model file trust** (§2.2 last row) and **TOCTOU** around tessdata and helper discovery.
- **The `system-tesseract` feature** links whatever `libtesseract` pkg-config finds; its version, build options (OpenMP on, in most distributions), thread behaviour and output silencing are outside our control. It is a source-build convenience with `BackendInfo.linkage = System`; the §13.5 silence test and the pool's behaviour are verified against the vendored build only, and a distribution build with OpenMP may oversubscribe (C5) — documented, not defended.
- **`fork()` while another thread is constructing or holding engine state.** A fork while another thread is inside the first `default_ocr_engine()` construction (the global-init `OnceLock`, tens to hundreds of milliseconds), or holds the pool, `LOG` or `TEST_ENV` mutex, leaves that lock held forever in the child, which then deadlocks (unit 08 reproduced the `OnceLock` case; units 08–09 the others). O11/O30 handle the pool *after* the child's first checkout; they cannot help a child that never gets that far. Mitigation: build engines before forking, or use the `spawn` start method with `multiprocessing`. Documented rather than defended: no `atfork` handlers are installed.
- **JBIG2 and JPEG 2000 memory.** H13 bounds the output of every codec by the declared, codec-header and reported dimensions, but not a JBIG2 region, symbol, pattern or halftone bitmap, nor JPEG 2000's per-tile records (§2.2, renderer row; revision (3)).
- **A near-blank, noisy page at 300 dpi stalls Tesseract for about 16 s** (unit 13: `sparse_below_min_chars_noise`, one text line under σ = 12 noise, CER 0.93), independent of the model (`tessdata_fast`, `best` and the combined file alike); the same page at 150 dpi takes 0.1 s. Bounded by `page_timeout` and, under `extract()`, by `max_ocr_pages`; no pre-check for sparse or blank pages exists.
- **A deadline that expires after the engine's last check.** `ocr_with` checks the deadline after the render and again after the noise pre-check, but the in-process backend then still runs `set_image` and two parameter calls before `Instance::recognize`. A deadline that expires inside that window reaches the sys crate as a zero remainder, which it refuses as `Timeout` without entering Tesseract (*added 2026-10-21*, internal #117 item 4). `pool::run` drops the instance after any `Err`, so this looks the same as a monitor stop. A timing test that treats "instance dropped" as proof the monitor stopped Tesseract can therefore be satisfied by this window for one attempt. Not defended: keeping the instance when nothing entered Tesseract would change the wording of O10.
- **Process-mode frame decoding (trusted helper).** Frame counts are capped per level at `MAX_COUNT` = 2^20 and the payload at 64 MiB, but an empty block or line is 4 bytes on the wire and a 24-byte `Vec` in memory, so a frame from the helper can decode to about six times its size (derived from the type sizes, not measured; about 384 MiB for a full frame, on top of the 64 MiB payload buffer). The helper is trusted (§2.2); a hostile one is out of scope (*added 2026-10-21*, internal #56 B13). Writes to a dead helper cannot raise `SIGPIPE` in the host (`pipe::write`: `F_SETNOSIGPIPE` on macOS, the signal blocked and consumed on Linux), so that exposure is defended, not a residual.
- **Helper spawn cost under a high descriptor limit.** Where `close_range` is unavailable (macOS, Linux before 5.11), `pipe::sweep_cloexec` marks descriptors close-on-exec one `fcntl` pair at a time up to the sweep bound (at most `MAX_SWEEP` = 2^20), so a high soft `RLIMIT_NOFILE` makes each helper spawn slower (about 130 ms per macOS spawn was reported in internal #56 B12; not re-measured). Not defended: a per-process descriptor listing or `POSIX_SPAWN_CLOEXEC_DEFAULT` would avoid it (*added 2026-10-21*, internal #56 B12).
- **Timeout lateness.** Tesseract checks its monitor deadline between recognition work units but **not during layout analysis**, so a timeout can be late by a whole layout pass (unit 06: a 1 ms deadline on 2000 × 2000 noise returned after about 3 s). Under `Isolation::Process` the parent's `poll` deadline is exact and the helper is killed (O27).
- **Everything 0001 §2.4 lists** still holds (allocation failure aborts; TOCTOU at open; module init unguarded; etc.).

### 2.5 Accuracy residuals (approximate components)

OCR is an approximation of the page's text, and our render is an approximation
of the oracle's. These are expected differences, not findings:

- **Text parity with the oracle's OCR is not a goal** (§7.1): the rasteriser (vello_cpu vs MuPDF), anti-aliasing, Tesseract build and model all differ; the §13.4 gate is an error-rate comparison on corpus D, not string equality. Line and block segmentation come from Tesseract's layout analysis, so `text()` of an OCR page has the same *shape* as the text path (O18) but line breaks need not match the oracle's.
- **Fonts hayro cannot render**: non-embedded CID fonts (design-spec §17.1) and embedded programs skrifa rejects draw as nothing or as the substitute's glyphs, so OCR of such pages differs from the oracle's. Such pages almost always have a text layer, so `extract()` rarely reaches OCR on them; corpus D tracks one example.
- **Rendering differences that change recognition**: hinting (none in vello_cpu), stroke adjustment, blend modes hayro approximates, and image resampling filters (CatmullRom in hayro, unknown in MuPDF) move edge pixels; at 300 dpi these are below Tesseract's sensitivity on clean text and are what the 1-CER-point tolerance of O34(a) absorbs at 72 dpi.
- **Model dependence**: every number in §13.4 is for the model files named in the measurement table (O35); a deployment with a different `eng.traineddata` gets different text. `info().model_sha256` is how a deployment knows which.
- **Word boxes** are Tesseract's word boxes split evenly over the word's code points (O17); per-glyph geometry for OCR text is approximate and `#[doc(hidden)]`.
- **Right-to-left and vertical scripts**: Tesseract's reading order for `eng` models on such pages is unmeasured; corpus D is Latin-script.
- **Weaknesses of the corpus-D quality gates** (B24 of internal #55; the gates stand as written, nothing here changes a threshold):
  - Gate (a) is reading-order sensitive. The oracle's 72-dpi output interleaves the two columns of the two-column pages, so its CER there is about 0.73 against about 0.02 for ours; the parity comparison measures reading order as much as recognition. `quality.rs` therefore also reports, never gates, an order-insensitive word-multiset F1 (`bow_f1` in `quality/metrics.rs`: F1 of precision and recall over the bags of whitespace-split tokens, same normalisation as D-10) per page and per subset for oracle@72, ours@72 and ours@300, as the evidence for any future order-insensitive gate.
  - Measured `bow_f1` means per subset (internal #97 C8; host-dependent, as every figure here): ours@72 0.81-0.94, oracle@72 0.72-0.92, ours@300 at least 0.99. Exact-token F1 is poor at 72 dpi on 9 pt text, where one wrong glyph voids a token, so it would make a poor gate unless made tolerant (a fuzzy token match); it stays report-only, consistent with ADR 13 and the timing figures. The per-subset table goes to stderr, so a run needs `--nocapture` to show it (the `corpus-d` job passes it); the same values are in `ocr-report.json` under `summary.<subset>.bow_f1_{oracle72,ours72,ours300}`.
  - The 72-dpi noise case is a weak test of noise. The σ = 12 field is added at 300 dpi and the page is then rendered down to 72 dpi, where the box filter leaves an effective σ of about 2.9; the noise subset's ours@72 CER (0.038) stays close to the clean subset's (0.032), and its gate (a) says little about noise robustness. Noise at 300 dpi is exercised by the pre-check pins (§2.3) and is measured and reported (the `ours@300` figures of `ocr-report.json`; *revised 2026-10-21*, internal #99 D2: the earlier "only by the pre-check pins" was wrong), but gate (a) does not gate it.
  - The `clean_numbered_list` column split is Tesseract's layout analysis reading the column of item numbers as a block of its own (CER 0.04-0.10 across its variants). It is not a pipeline defect and will not be fixed here.
- **Timeout granularity**: Tesseract polls the monitor between work units, so `OcrTimeoutError` arrives up to one unit (a text line, in practice well under a second) after `page_timeout`, or a whole layout pass late (§2.4); in process mode the parent's `poll` deadline is exact and the kill is immediate.

No universal claim is made over the space of all PDFs, all images or all
model files. The gates in §4 are the claim.

### 3.2 Dependencies and fork changes

**The rasteriser: `hayro = "=0.7.1"` from crates.io, not vendored.** Verified

**Build (`crates/tesseract-sys/build.rs`, feature `vendored`, default).** No
network, no system Leptonica/Tesseract consulted. Using the `cmake` crate
(0.1.x), build Leptonica first:
`-DBUILD_SHARED_LIBS=OFF -DBUILD_PROG=OFF -DSW_BUILD=OFF -DENABLE_ZLIB=OFF
-DENABLE_PNG=OFF -DENABLE_GIF=OFF -DENABLE_JPEG=OFF -DENABLE_TIFF=OFF
-DENABLE_WEBP=OFF -DENABLE_OPENJPEG=OFF` (no codecs: pixels arrive through
`SetImage`; the only link dependency is `libm`), then Tesseract with
`-DBUILD_SHARED_LIBS=OFF -DBUILD_TRAINING_TOOLS=OFF -DDISABLE_TIFF=ON
-DDISABLE_ARCHIVE=ON -DDISABLE_CURL=ON -DGRAPHICS_DISABLED=ON
-DDISABLED_LEGACY_ENGINE=ON -DOPENMP_BUILD=OFF -DENABLE_LTO=OFF
-DENABLE_NATIVE=OFF -DINSTALL_CONFIGS=OFF -DENABLE_CCACHE=OFF
-DENABLE_PRECOMPILED_HEADERS=OFF -DLeptonica_DIR=<leptonica install>/lib/cmake/leptonica`
and `CMAKE_BUILD_TYPE=Release`. Why each: `DISABLED_LEGACY_ENGINE` removes the
legacy classifier, whose template loader is the only `exit()` on a model-load
path, and halves the object code; `GRAPHICS_DISABLED` removes ScrollView and its
`exit(0)`; `OPENMP_BUILD=OFF` keeps C5 (no `libgomp`/`libomp`, no hidden
thread pool); `ENABLE_NATIVE=OFF` keeps wheels portable — Tesseract compiles its
AVX/AVX2/AVX-512/SSE4.1 kernels per file and dispatches by `cpuid` at run time,
and uses NEON unconditionally on aarch64, so `-march` is irrelevant; the
`DISABLE_*` flags drop libtiff/libarchive/libcurl, which only the CLI and
URL/zip model loading use. (*Added 2026-10-21*, internal #56 D4: `build.rs` builds the
`libtesseract` target only, `build_target("libtesseract")`, so the command-line
program that Tesseract's CMake configuration also defines is not compiled.) The build needs CMake ≥ 3.18 and a C++17 compiler
(GCC ≥ 11, Clang ≥ 18 or Apple clang from Xcode 16 per Tesseract's supported
list; manylinux_2_28's gcc-toolset qualifies). `build.rs` emits
`cargo:rustc-link-lib=static=tesseract`, `=static=leptonica`, `=m`, and the
platform C++ runtime (`c++` on macOS, `stdc++` on Linux), plus
`cargo:rerun-if-changed` on both vendored trees and the shim. The output lands
in `OUT_DIR`, so `Swatinem/rust-cache` caches it between CI runs (§3.7).

**Consequence of `DISABLED_LEGACY_ENGINE`:** `EngineMode::TesseractOnly` and
`TesseractLstmCombined` are refused by the vendored build at engine construction
with `OcrUnavailable { reason: InitFailed, detail: "legacy engine not built" }`
before calling `Init`; `LstmOnly` and `Default` (which is LSTM in such a build)
work. All three model families load: `tessdata_fast`, `tessdata_best` and the
combined `tessdata` set (its LSTM part is used — stated by Tesseract's guards,
**unverified by execution** until unit 06's test runs on the MacPorts
23.5 MB `eng.traineddata`, which is the combined set).

**The shim (`crates/tesseract-sys/csrc/shim.cpp`, ≈200 lines, C++17).** Every
exported function is `extern "C"`, takes and returns only C types, and wraps
its body in `try { … } catch (const std::exception& e) { copy e.what() into the
caller's buffer; return PXT_ERR_EXCEPTION; } catch (...) { return
PXT_ERR_EXCEPTION; }`. Tesseract's own `capi.h` has **no** `try/catch`
(Appendix B.2), so a `std::bad_alloc` thrown inside `Recognize` would otherwise
unwind into Rust, which is undefined behaviour; the shim is therefore the only
C/C++ entry point Rust calls — `capi.h` is not bound at all, the shim calls
`tesseract::TessBaseAPI` directly. Functions: `pxt_version()`,
`pxt_global_init(const char* debug_null_path, char* err, size_t err_len)` (every function that can fail carries an `(err, err_len)` pair; sets `debug_file`, installs
Leptonica's `leptSetStderrHandler` no-op; called under a Rust `Once`),
`pxt_create()`, `pxt_init(h, datapath, langs, oem, const char** var_names,
const char** var_values, size_t n)` (`Init` with `set_only_non_debug_params =
false`, so a future debug variable can still be passed), `pxt_set_image(h, data,
w, h, bytes_per_pixel = 1, bytes_per_line)` (builds and checks the Leptonica `Pix` itself and refuses an image of 2³¹ bytes or more, because upstream `Thresholder::SetImage` dereferences a null `Pix` when `pixCreate` fails), `pxt_set_resolution`,
`pxt_set_psm`, `pxt_recognize(h, deadline_ms) -> int` (creates an `ETEXT_DESC`,
`set_deadline_msecs`, runs `Recognize`; returns 0, `PXT_ERR_TIMEOUT` when
`Recognize` returned −1 **and** the monitor's deadline has passed by our own
clock, `PXT_ERR_RECOGNIZE` otherwise), the iterator walk as one call
`pxt_collect(h, callback, user_data)` that invokes a Rust `extern "C"` callback
per word with `(level_flags, text, len, l, t, r, b, confidence)` — flags mark
the start of a block and of a line, so the Rust side builds the tree without
holding C pointers across calls — `pxt_clear`, `pxt_end`, `pxt_delete`,
`pxt_model_checksum`-free (checksums are computed in Rust). The Rust callback
is `catch_unwind`-wrapped and never panics across the FFI. Error strings are
copied into a fixed 512-byte caller buffer; nothing is allocated across the
boundary except Tesseract's own text, freed by the shim inside `pxt_collect`.

**Why a shim rather than `tesseract-sys`/`leptonica-sys` from crates.io:** both
bind a *system* library via bindgen and pkg-config and vendor nothing; bindgen
would add a build-time dependency on libclang; and neither catches exceptions.
`tesseract-rs` downloads sources at build time (network in `build.rs`), which
the hermetic build forbids. The shim is small enough to review in one sitting
and is covered by Rust tests through the public backend.

**Feature `system-tesseract`** (mutually exclusive with `vendored`; `build.rs`
fails with a clear message if both or neither are on): `pkg-config` for
`tesseract` (which requires `lept` privately) and a check that the found
Leptonica is ≥ 1.79.0 (the first release with `leptSetStderrHandler`; Tesseract's
own floor is 1.74) and Tesseract ≥ 5.3 (`capi.h`-era API; **5.3 is the oldest
version the shim is written against, unverified below 5.5**). The shim is
compiled against the system headers; `BackendInfo.linkage = System`. On the
development machine MacPorts provides `tesseract.pc` (which links
`-larchive -lcurl`, both present) and `lept.pc`. The feature exists for source
builds and distribution packaging; wheels never use it, and §2.4 lists what it
cannot promise.

**Unsafe inventory.** `pdf-extract-tesseract-sys` is the only crate besides
`crates/python` that compiles `unsafe`: the `extern "C"` declarations and the
calls to them, each with a `// SAFETY:` comment naming the invariant (handle
non-null and owned by this `Instance`; image slice length equals `h ×
bytes_per_line`; callback pointer lives for the call). `pdf-extract-ocr` and
`pdf-extract-render` are `#![forbid(unsafe_code)]`. The `Instance` type owns
the handle, is `Send` (Tesseract instances are independent, Appendix B.2) and
not `Sync`, and calls `pxt_end` + `pxt_delete` in `Drop`.

**Process-wide state we touch:** `debug_file` (a Tesseract global `STRING_VAR`;
set once by `pxt_global_init` under the `Once`, never again) and Leptonica's
stderr handler (a plain global function pointer; same `Once`). We never call
`SetVariable` with any of Tesseract's remaining process-global parameters (the
file-scope `*_VAR`s in `textord`/`wordrec`, which are debug toggles); every
per-instance variable goes through `Init`'s `vars_vec`. `Dict::GlobalDawgCache`
is shared between instances and ref-counted; whether its internal locking is
sound under concurrent `Init` is **unverified** — unit 06's concurrency test
(N threads each constructing and destroying engines) is the probe, and a
finding there becomes a serialised `Init` (a `Mutex` around `pxt_init` only).

### 3.5 The helper process protocol (`Isolation::Process`)

**Transport.** One helper per pool slot; the parent spawns
`pdf-extract-ocr-helper` with `stdin` and `stdout` as pipes and `stderr` as
the null device, no arguments, and an environment of exactly: `TESSDATA_PREFIX`
(the resolved directory, so the child never re-resolves), `LANG`/`LC_ALL` if
set in the parent, `PDF_EXTRACT_OCR_HELPER_FAULT*` only when the parent's
process environment has them (test hook, O31). All other variables are dropped
(`Command::env_clear`).

**Framing.** Every message is `magic: [u8; 4] = b"PXO1"`, `kind: u8`,
`reserved: [u8; 3]`, `len: u32 LE`, then `len` bytes of payload. `len` ≤
64 MiB (`MAX_FRAME`); a larger declared length is a protocol error on the
receiving side (parent: `OcrPageError::Recognition("helper: frame too
large")`, child: exit 2). Payloads are fixed-layout little-endian structs
followed by length-prefixed UTF-8 strings; no serialisation library is used
(the crate graph stays as it is and the format is reviewable in one file,
`crates/ocr/src/isolation/wire.rs`, which both sides compile).

| kind | Direction | Payload | Reply |
|---|---|---|---|
| `0x01 Hello` | parent → child | `proto_version: u32 = 1`, `oem: u8`, `psm: u8`, `languages: str`, `tessdata: str`, `debug_null: str` | `0x81 HelloOk { tesseract_version: str, library_version: str, model_sha256: [(str, [u8;32])] }` or `0x82 HelloErr { reason: u8, detail: str }` |
| `0x02 Recognize` | parent → child | `width: u32`, `height: u32`, `dpi: u32`, `psm: u8`, `deadline_ms: u32` (relative), then `width × height` bytes | `0x83 Result { blocks: [ { lines: [ { words: [ { bbox: [u32;4], confidence: f32, text: str } ] } ] } ] }` (counts as `u32`, each ≤ 2²⁰), or `0x84 PageErr { kind: u8 /* 0 recognition, 1 timeout */, detail: str }` |
| `0x03 Shutdown` | parent → child | empty | child exits 0 after `End()` |

**Rules.**

- Exactly one request is in flight per helper; the parent owns the slot while
  it waits. The parent reads the reply with a deadline of `page_timeout`
  measured from the start of the `ocr()` call (so rendering time is counted)
  plus a 2 s grace for transport; on expiry it sends `SIGKILL`, reaps the
  child, marks the slot dead and returns `OcrPageError::Timeout`.
- Any read error, EOF, bad magic, unknown `kind`, over-cap `len`, bad UTF-8,
  or count over the cap: the parent kills (if alive) and reaps the child, marks
  the slot dead, and returns `OcrPageError::Recognition("helper …: <what>")`
  with the exit status if known (`helper exited: signal 6 (SIGABRT)` for the
  injected abort).
- The child validates `proto_version` (mismatch → `HelloErr { reason:
  engine_not_built }` and exit 2), image sizes (`width × height == payload len`, both
  ≥ 1, else exit 2), and runs the same shim as the in-process backend. It
  writes the null device path from `Hello` into `debug_file` before `Init`.
- Dead slots are respawned lazily at the next checkout (O27); a spawn failure
  (`ENOENT` because the binary vanished, `EMFILE`) is `OcrUnavailable {
  reason: EngineNotBuilt }` from that call.
- `Drop` of the pool sends `Shutdown` to idle helpers and waits up to 2 s each,
  then kills; busy helpers (another thread is inside `ocr()`) are left to their
  caller, whose slot is returned to a pool that no longer exists and is then
  shut down the same way.
- Test-only fault modes beyond O31's are `slow-on-recognize:<ms>` and `report-env` (and `report-fds`). A respawned helper's start-up is allowed `max(page_timeout, 60 s) + 2 s`, outside the page's budget. The `unsafe` the protocol needs (pipes, `poll`, the pre-exec descriptor sweep) lives in `crates/tesseract-sys/src/pipe.rs`. The helper's protocol version is checked at engine construction, so a wheel
  whose extension and helper disagree fails fast with `EngineNotBuilt` naming
  both versions.

**Why pipes and a bespoke frame rather than a socket or an existing IPC crate:**
no new dependency with its own licence and `unsafe`, no filesystem path to
clean up, inheritance semantics identical on Linux and macOS, and `poll(2)` on
a pipe gives the deadline. The protocol is internal: the helper and the
library ship together and are version-locked (`HelloOk` carries the build's
`pdf_extract_core::VERSION`; a mismatch is `EngineNotBuilt`).

### 3.8 Corpus D and the OCR expectations

**What corpus D is.** A synthetic corpus of **image-only PDFs with known
ground truth**: text pages produced by the Rust test kit (Helvetica WinAnsi
text, deterministic bytes; `testkit::corpus_d::sources()`) are rasterised by
the **oracle's** renderer (`page.get_pixmap(dpi=300, colorspace=csGRAY)`, so
the scan does not come from our own rasteriser), optionally degraded, and
re-wrapped as one grayscale image per page (`insert_image`, FlateDecode; PyMuPDF writes the clean images as `[/ICCBased N=1]`, while the built noise variants are `/DeviceGray`, and `noise_variant` accepts both). The
ground truth is the text the builder was given, written to
`tests/fixtures/corpus-d/<name>.txt` alongside the PDF. PyMuPDF randomises
`/ID` on save, so these PDFs are **not byte-reproducible**:
`tools/oracle/mkcorpusd.py` is run once per recipe change and the files are
committed with their SHA-256 in `manifest.toml` (`gate = "ocr"`, `generator =
"tools/oracle/mkcorpusd.py::<subset>"`), the same treatment as the encrypted
fixtures (0001 T51). **Forty of the 52 files are committed this way. The
twelve noise variants are not committed at all**: the test kit builds them at
test time from the committed clean files (below), because at 55.1 MB measured
they do not fit Q4's cap.

**Recipes** (Appendix C lists each file): 12 clean pages (body text at 9, 10,
11, 12 pt; a two-column page; a page with a heading and a footnote; a
numbered list; a page with digits and punctuation dense enough to measure
reporter-citation style strings like `123 F.3d 456 (9th Cir. 2001)`; a mostly
empty page with one line; a rotated (`/Rotate 90`) page; a CropBox page; a page
whose text falls below `min_chars` to exercise routing), each also as a
**noise** variant (Gaussian σ = 12 gray levels, seeded; built at test time),
a **skew** variant (rotation of +1.5° about the centre, bicubic, white fill)
and a **blur** variant (Gaussian radius 1.2 px at 300 dpi); plus 3 pages at
**150 dpi** source resolution (so that "ours at 300" renders an upscaled
image, as real low-resolution scans do) and 1 page whose image is JPEG
(DCTDecode, quality 75) to exercise that decoder. **Sizes, measured by unit
12** (8-bit gray at 300 dpi, FlateDecode): the 12 clean + 3 low-resolution +
1 JPEG pages are 5.1 MB, skew 9.3 MB, blur 7.8 MB — **22.2 MB committed**,
under the 25 MB cap; the 12 noise variants would have added 55.1 MB (≈ 4.7 MB
each: additive noise at σ = 12 carries 3–4 bits of entropy per pixel, which
no lossless filter removes). Skew, blur and the JPEG encoding need Pillow and
numpy: both are added to `tools/oracle`'s dev-only `pyproject.toml` (never to
the library; L2 unchanged), pinned exactly like PyMuPDF, and the project's
`requires-python` rises from 3.11 to 3.12, which numpy 2.5 requires. **Noise
is made only in Rust**: `mkcorpusd.py` has no noise step (a Python
re-implementation could not be bit-identical to the Rust one and would verify
nothing but itself); its `--verify` checks the Rust-built files through the
oracle instead.

**The noise variants** live in `testkit::corpus_d`; `hayro-syntax` and `sha2`
move from the test kit's dev-dependencies to its dependencies (both are
already in every build that links core, so the graph does not change). For
each of the 12 sources, `noise_variant(clean_pdf)` opens the committed clean
file with `hayro_syntax::Pdf`, takes the page's single image XObject and
`Stream::decoded()` (FlateDecode, no predictor), requires `/BitsPerComponent
8`, `/ColorSpace /DeviceGray` and exactly `width × height` bytes (anything
else, including a text layer or a second image, is `BuildError`), adds noise
to the samples in place, and writes a new one-page PDF. That is a Flate
decode of the oracle's pixels, not a rasterisation, so D-9 still holds: no
corpus-D pixel is ours.

*Noise model.* PRNG: SplitMix64 (`state += 0x9E3779B97F4A7C15`; `z = state`;
`z = (z ^ (z >> 30)) × 0xBF58476D1CE4E5B9`; `z = (z ^ (z >> 27)) ×
0x94D049BB133111EB`; output `z ^ (z >> 31)`; all wrapping `u64`), state set to
`NOISE_SEED = 20261003` at the start of every file (the Python recipe
reseeded per file too), one deviate per pixel in row-major order. Deviate: the
Irwin–Hall approximation to a Gaussian — `S` is the sum of 12 draws of `next()
>> 44` (20-bit uniforms), `d = S − 6 × (2^20 − 1)` (exact mean 0, variance
`2^40 − 1`), `n = (12·d ± 2^19) div 2^20` with truncating division and the
sign following `d` (round to nearest, ties away from zero), so σ = 12 ×
√(1 − 2^−40) ≈ 12.000 and |n| ≤ 72; the pixel becomes `clamp(p + n, 0,
255)`. Integer arithmetic throughout, so the bytes are identical on every
host: Box–Muller would go through `ln`/`cos`, whose last bits differ between
libms, and a pinned hash needs byte identity. The approximation is the
textbook one (excess kurtosis −0.1, density error below 10⁻³ everywhere) and
the σ is the Python recipe's. For seed 20261003 the first eight deviates are
`5, −21, 10, −16, −18, −7, −17, 6`; a unit test asserts them, and the moments
of a 2480 × 3509 field of 128s: |mean| < 0.05 and |σ − 12| < 0.05 (the
rounding adds 1/12 to the variance; expected σ ≈ 12.003).

*Assembly* (`pdfwriter::Objects`, as `hostile.rs` does it): `%PDF-1.4`;
objects 1 catalog, 2 pages, 3 page, 4 image, 5 content, in that order; the
page carries the clean file's `/MediaBox`, its `/CropBox` when that differs
and its `/Rotate` when non-zero (`Page::media_box`/`crop_box`/`rotation`,
written with `pdfwriter::num`); the image dictionary is `/Type /XObject
/Subtype /Image /Width w /Height h /ColorSpace /DeviceGray /BitsPerComponent
8` with **no filter** — raw samples, because Flate saves under 2× on noise
and would make the hashes depend on the deflate implementation's version; the
content is `q W 0 0 H x0 y0 cm /Im0 Do Q` over the MediaBox `[x0 y0 x1 y1]`;
no `/ID`, `/Info` or dates; a classic xref table. The 12 files are ≈ 8.7 MB
each (≈ 105 MB in all) and live in `target/corpus-d/`
(`corpus_d::default_build_dir()`: `$CARGO_TARGET_DIR`, else
`<workspace>/target`), never under `tests/fixtures/`. Files are written to a
temporary name and renamed into place, so two test binaries building at once
never read a partial file.

*Pinning.* Each built file's SHA-256 is pinned in `manifest.toml` in a new
array `[[built]]` with keys `path` (relative to the build directory, e.g.
`clean_body_11pt_noise.pdf`), `sha256`, `generator = "testkit::corpus_d::noise"`,
`gate = "ocr"`, `subset = "noise"`, and `source` and `truth` (the `[[fixture]]`
paths of the committed clean PDF and its ground truth; a noise variant has no
`.txt` of its own). `[[fixture]]` keeps meaning "a committed file";
`fixtures_manifest.rs` checks `[[built]]` rows the other way round: the keys
are present, `tests/fixtures/corpus-d/<path>` does **not** exist, `source`
and `truth` are `[[fixture]]` paths, and the set of `path`s equals
`corpus_d::noise_names()` with `.pdf` appended. The pins are the only copy of the hashes; the Rust
side carries none. The API:

```rust
pub mod corpus_d {                                     // additions
    pub const NOISE_SEED: u64 = 20261003;
    /// `"<source>_noise"` for each source, catalogue order.
    pub fn noise_names() -> Vec<String>;
    /// The noise model above, in place over 8-bit gray samples.
    pub fn add_noise(gray: &mut [u8], seed: u64);
    /// The noise variant of a committed clean file: pixels and boxes from
    /// the file, never its bytes, so a clean regeneration (new `/ID`) does
    /// not move the pin.
    pub fn noise_variant(clean_pdf: &[u8]) -> Result<Vec<u8>, BuildError>;
    pub fn default_build_dir() -> PathBuf;             // target/corpus-d
    pub struct Built { pub name: String, pub path: PathBuf, pub sha256: String, pub pinned: Option<String> }
    /// All twelve into `out`; `pins` are the `(name, sha256)` pairs the
    /// caller read from `manifest.toml` `[[built]]`. A file already in `out`
    /// whose hash equals its pin is reused; anything else is rebuilt from
    /// `<fixtures>/corpus-d/<source>.pdf`. Never fails on a mismatch: the
    /// caller compares `sha256` with `pinned` and decides.
    pub fn build_noise(fixtures: &Path, out: &Path, pins: &[(&str, &str)]) -> Result<Vec<Built>, BuildError>;
}
```

*Commands* (`gen.py` and `mkcorpusd.py` read the pins from `manifest.toml`):

- `cargo run -p pdf-extract-testkit --example corpus_d_noise -- <dir>` builds the 12 files into `<dir>` and prints `<sha256>  <path>  ok|DRIFT|unpinned` per file. It is the producer, not the check: exit 0 whenever the files were written.
- `uv run python mkcorpusd.py --pin-built <dir>` hashes the files in `<dir>` and writes the `[[built]]` rows into the manifest's corpus-D block and a "built at test time" row per file into the PROVENANCE table.
- `uv run python gen.py --ocr --tessdata <dir> --built <dir> tests/fixtures/corpus-d` adds the built files to the run: for every `[[built]]` row it reads `<dir>/<path>`, **refuses the whole run before writing anything** when the file's SHA-256 differs from the row, and otherwise writes `expectations/<sha256>.json` with `source = "built/<path>"` and the `ocr` block. An expectation can therefore only ever be produced from pinned bytes.
- `uv run python mkcorpusd.py --verify --built <dir>` runs the oracle checks on the built files too (image-only, one 8-bit gray image, no `/Filter`, the source's boxes and rotation, dimensions as expected) plus the hash check against `[[built]]`.

*Drift checks at test time.* (1) `crates/testkit/tests/corpus_d_noise.rs`
(runs in the `rust` job, needs no tessdata) calls `build_noise` into
`default_build_dir()` and asserts every hash equals its pin. (2) `quality.rs`
does the same before scoring and fails on a mismatch, naming the file, both
hashes and the re-pin steps — the expectation keyed by the pin would belong
to other bytes. (3) `gen.py --built` refuses unpinned bytes as above. Taken
together, the committed expectation, the pinned hash and the bytes a test
scores are the same file, or something fails. **Re-pin procedure** after a
recipe or noise change: `mkcorpusd.py` (40 files) → `corpus_d_noise` →
`mkcorpusd.py --pin-built` → `gen.py --ocr --built` → `mkcorpusd.py --verify
--built` → commit. Regenerating the clean files alone leaves the pins valid.

**Expectations.** `tools/oracle/gen.py --ocr --tessdata <dir>` adds to each
corpus-D expectation file — committed files and, with `--built <dir>`, the
Rust-built noise variants — an `ocr` block: `{ "dpi": 72, "language": "eng",
"tessdata_sha256": "<hex of eng.traineddata>", "pages": [ { "index", "text",
"sha256" } ] }` from `page.get_textpage_ocr(full=True, language="eng",
dpi=72, tessdata=<dir>)` — passed explicitly, because PyMuPDF's own discovery
needs `tesseract` on `PATH` (Appendix A.3). The schema version becomes 2;
schema-1 files stay valid (no `ocr` block). The oracle's OCR is deterministic
in-process (probed three times at 72 dpi), so the committed value is stable
for a given model file; the model is the `tessdata_fast` `eng.traineddata`
named in §3.7 and D-17 — git blob `bbef4675053b5b468cdb477053e28b1c698ba08e`,
SHA-256 `7d4322bd2a7749724879683fc3912cb542f19906c83bcc1a52132556427170b2` —
downloaded into the oracle project's cache by `mkcorpusd.py --fetch-model`
and checked against both digests. Every committed expectation's
`tessdata_sha256` equals that SHA-256; it is the one model the committed
numbers and the CI gate are valid for, and the field ties every number to it.

**The gate** (`crates/ocr/tests/quality.rs`, CI job `corpus-d`): build the
noise variants with `corpus_d::build_noise` and stop on any pin mismatch;
then for every `gate = "ocr"` fixture and every `[[built]]` row, run
`Page::ocr` at 72 and at 300 dpi with the `tessdata_fast` model, compute
CER/WER against the ground truth (D-10; NFC through `unicode-normalization`,
a dev-dependency of `pdf-extract-ocr` only — MIT OR Apache-2.0, new to the
lockfile, already on `deny.toml`'s allow-list), read the oracle's 72-dpi text
from the expectation and compute its CER/WER against the same ground truth,
then apply O34 (a)–(c) over the corpus means, and write
`target/ocr-report.json`. The test is `#[ignore]` by default (it needs
tessdata) and run with `--include-ignored` by the job and by developers; it
skips with a clear message when `TESSDATA_PREFIX` resolves to nothing.
Latency per page and RSS per instance are in the report and printed, never
asserted (ADR 13).

**Private scans.** `tools/oracle/run_private_scans.sh <dir> [<out>]` mirrors
`run_private_corpus.sh`: it refuses paths inside the repository, runs the
oracle's 72-dpi OCR over every PDF under `<dir>` into `<out>/expectations`
(no ground truth exists for real scans, so the metric is **agreement**: the
character similarity between our 72-dpi text and the oracle's, and between our
300-dpi text and the oracle's, per page), runs the ignored
`quality::private_scans` test in release, prints median/p10 similarity and
the routing agreement at `min_chars = 50` (whether both sides would call the
page sparse after OCR), and writes a report that holds lengths and
similarities only, never text. The thresholds are **report-only** in this run
(no ground truth, and the user's scans are the first real OCR data the
project sees); a gate is proposed in a follow-on once numbers exist.

### 4.9 Unit 09 — process isolation

- `wire.rs` round-trips every message through `encode → decode` (property test over random words, boxes, lengths); a frame with bad magic, a `len` of `MAX_FRAME + 1`, a truncated payload, a count of 2²⁰ + 1, and invalid UTF-8 each decode to the documented error.

### B.4 Image codecs behind H13 (vendored `hayro-syntax/src/filter/{ccitt,dct,jbig2,jpx}.rs`; registry copies `hayro-ccitt-0.3.0`, `hayro-jbig2-0.3.0`, `hayro-jpeg2000-0.3.5`, `zune-jpeg-0.5.15`, as locked; checked 2026-10-03)

Where each codec's output size first becomes known, and what it allocates
before and after that point. "Output" is the buffer the filter module
returns; hayro-interpret then pads or truncates it to the `ImageData` width ×
height the module reports (`x_object.rs` `fix_image_length`) and converts it
to RGBA, so the reported size governs the conversion buffers.

- **DCT** (`dct.rs`, zune-jpeg): `maybe_patch_jpeg_dimensions` reads the frame size from the first `SOF` marker and, when `jpeg_width × jpeg_height` exceeds the declared `/Width × /Height`, rewrites the marker to the declared dimensions before zune sees the data; `JpegDecoder::decode_headers()` allocates no pixel buffer and `decode()` allocates `output_buffer_size()` = width × height × components (`decoder.rs:215-217`); zune also refuses either side over `u16::MAX`. So the JPEG's area is at most the declared area and the declared check already bounds this codec; `decoder.dimensions()` is available after `decode_headers()`. Reported `ImageData` = zune's dimensions.
- **CCITT** (`ccitt.rs`, hayro-ccitt): the size is dictionary-driven and known before `hayro_ccitt::decode` is called: `columns = /Columns` (default 1728, any `u32`), `rows = /Rows`, else the declared height. hayro-ccitt itself allocates only the per-line change lists (≤ `columns` entries); the output `Vec` is the filter module's `Decoder` implementation, grown per pixel (one byte per pixel on the 8-bit path; `push_pixel_chunk` extends by `8 × chunk_count` bytes), with runs clamped to the line width (`lib.rs:457-459`). Stop condition `decoded_rows == rows || at_end` (`lib.rs:249, 267`): Group 4 tests it before each row, so `rows == 0` decodes nothing; Group 3 tests it after each row, so `rows == 0` runs to the end of the data, at no fewer than two bits per row (tag bit plus one mode code), i.e. ≤ `4 × data.len()` rows. Reported `ImageData` = `columns` × **declared height** (`height: image_params.height`), so the conversion buffer can differ from both the declared and the decoded size.
- **JBIG2** (`jbig2.rs`, hayro-jbig2): `Image::new_embedded` parses segment headers only (`parse_segments_sequential`), takes the page size from the page-information segment and resolves a height of `0xFFFFFFFF` from the largest end-of-stripe row + 1 (`lib.rs:136-172`); `width()`/`height()` are then available with nothing proportional to pixels allocated. The page bitmap is allocated in `decode` (`init_page` → `Bitmap::reinitialize`, `lib.rs:667-691`), one bit per pixel; the filter module's own `vec![0; row_bytes × height]` (indexed path) and the 8-bit output `Vec` follow. Every bitmap is limited to 65,535 a side (`bitmap.rs:15`, `MAX_DIMENSION`). **Not bounded by the page size**: region bitmaps (`decode/generic.rs:17`, `text.rs:29`, `halftone.rs:23`, `generic_refinement.rs:22`) are sized by their region-segment info and clipped only when composed onto the page (`bitmap.rs:135`, `combine`); symbol bitmaps (`symbol.rs:109, 257, 589-625`) by their height class and width; pattern dictionaries (`pattern.rs:30, 87`) by their own fields — each up to 512 MiB, with no limit on how many symbols a dictionary holds. Reported `ImageData` = page width × height.
- **JPEG 2000** (`jpx.rs`, hayro-jpeg2000): `Image::new` parses the main header only (`j2c::parse_raw` → `read_header`; for a JP2 wrapper the boxes first); the `SIZ` marker is validated (either side over 60,000 is `ImageTooLarge`, `codestream.rs:568-574`) and `width()`/`height()` are available with no tile or pixel allocation. They report the size `decode()` will allocate — width × height × channels bytes (`lib.rs:196-205`) — **after** the resolution reduction `target_resolution` requests (`image_width()` divides by the shrink factors, `codestream.rs:507-516`; hayro-interpret passes its `target_dimension` through). The working set does not shrink with it: `decode` first builds one `Tile` record per tile of the reference grid (`tile.rs:131-137`, called from `decode.rs:36`; a 1 × 1 tile grid means one record, holding a cloned `Vec<ComponentInfo>`, per full-resolution pixel), then per tile an `f32` coefficient buffer of Σ components (component-tile area) at **full resolution** (`build.rs:19-31`; `ComponentTile::rect` derives from the reference-grid tile rectangle, `tile.rs:330-360`, and the skipped levels only select which resolution tiles are decoded, `decode.rs:308`). A header-only `Image::new` with `target_resolution: None` yields the full-resolution size at the cost of one more header parse. Reported `ImageData` = the (reduced) width × height.
- **Byte cap**: `DecodeLimits::max_stream_decoded_bytes` (H2b) applies to the flate, LZW, run-length and ASCII filters only; the four image codecs are outside it by design (`filter/mod.rs`: `Filter::apply` passes `limit` to `limited()` for those five filters alone, and the `DecodeLimits` doc says so). It bounds none of the residuals above.
