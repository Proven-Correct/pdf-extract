# Oracle tooling

Developer-only tools that run the reference extractor, PyMuPDF 1.28.2, to
produce the expectations `pdf-extract` is measured against (run spec
`docs/specs/0001-text-path.md` §4.13, D-21).

## L2: black box only

- PyMuPDF/MuPDF is used **only** through its public Python API: open a file,
  read `page_count`, call `get_text("text")`, save an encrypted copy. Its
  source is never read, copied or translated, and nothing here is derived
  from it beyond observed outputs.
- This uv project is isolated on purpose. The library, its Rust and Python
  tests, and CI **never** import or install PyMuPDF and never use this venv.
  CI's `parity` job reads the committed JSON in `tests/fixtures/expectations/`.
- Expectations are generated locally, once per fixture change, and
  committed.

## Files

| File | Role |
|---|---|
| `mkfixtures.py` | Encrypted fixtures (`enc`), the Helvetica width vector (`--afm-check`), and `--verify` (every generated sample and committed fixture opens in the oracle as recorded). |
| `gen.py` | Writes `tests/fixtures/expectations/<sha256>.json` for every file under the given directories, opening each **from disk** (the oracle treats unsaved in-memory documents differently, spec Appendix A.3). Schema: spec §3.6 and the module docstring. |
| `score.py` | Pretty-prints `target/parity-report.json` (gate C) and `target/parity-report-b.json` (gate B), which `crates/core/tests/parity.rs` writes, or any one corpus report with `--gate-report`. Plain Python; needs neither PyMuPDF nor the library. |
| `run_private_corpus.sh` | The corpus-A run over a private directory (below). Never run on CI. |
| `mkcorpusd.py` | Corpus D, the OCR quality corpus (below): rasterises the test kit's pages with the oracle, degrades and re-wraps them; pins and checks the Rust-built noise variants; downloads the pinned OCR model (`--fetch-model`). |
| `run_private_scans.sh` | OCR agreement with the oracle on a private directory of scans (below). Never run on CI. |

## Regenerating corpus C

Corpus C (`tests/fixtures/corpus-c/`) is generated by the Rust test kit from
the catalogue in `crates/testkit/tests/common/corpus/`, which also holds each
fixture's compat points and gate. After changing a recipe or a gate:

```sh
# 1. Rebuild the fixtures and the generated section of manifest.toml.
cargo run -p pdf-extract-testkit --example corpus_c

# 2. Run the oracle over them (from tools/oracle; needs PyMuPDF).
cd tools/oracle
uv run python gen.py --prune ../../tests/fixtures/corpus-c ../../tests/fixtures/corpus-b
cd ../..

# 3. Pin our output for divergence and hostile fixtures, then check gate C.
PARITY_BLESS=1 cargo test -p pdf-extract-core --test parity
cargo test -p pdf-extract-core --test parity
python3 tools/oracle/score.py
```

`--prune` deletes expectations whose input no longer exists; pass every
directory that shares the expectations directory. `PARITY_BLESS=1` rewrites
only the snapshots of `divergence` and `hostile` entries; review their diff like code.
`cargo test -p pdf-extract-testkit --test corpus_c` proves the committed
files and manifest still match the catalogue.

The encrypted fixtures are the exception: `uv run python mkfixtures.py enc`
rewrites them, and since MuPDF randomises the file identifier and key on
every save, their hashes change, so rerun step 2 afterwards.

## Corpus B

`tests/fixtures/corpus-b/` holds files imported byte for byte from hayro's
and Apache PDFBox's test suites; `tests/fixtures/PROVENANCE.md` records the
upstream commit, path, license, hash and selection rule of each, and every
`manifest.toml` entry carries `origin`, `license` and `license_note`. After
adding or replacing a file there, add its entry and provenance row by hand,
then:

```sh
cd tools/oracle
uv run python gen.py ../../tests/fixtures/corpus-b     # no --prune: corpus C shares the directory
cd ../..
cargo test -p pdf-extract-core --test parity
python3 tools/oracle/score.py
```

To prune, name both corpora: `gen.py --prune ../../tests/fixtures/corpus-c
../../tests/fixtures/corpus-b`.

## Gates

`manifest.toml` gives each fixture a gate (spec §3.6, §4.13):

- `exact`: our open outcome class (opened, password required, failed) and
  every page's text equal the oracle's.
- `divergence`: a documented, deliberate difference (the `divergence` key
  cites the spec); our output must equal `snapshots/<sha256>.txt` and still
  differ from the oracle.
- `hostile` (D-27): the same open outcome class as the oracle, our output
  equal to its snapshot and exactly the `warnings` kinds; never compared
  with the oracle's text, which for hostile input depends on placement.

- `similarity` (corpus B): not judged file by file. Gate B scores every
  page of every such fixture together (spec §4.14): the oracle opened a file
  ⇒ we open it (at most two documented exceptions, `OPEN_EXCEPTIONS` in
  `crates/core/tests/parity/gate_b.rs`); the routing decision
  `len(text.strip()) >= 50` agrees on ≥ 99% of pages; the similarity
  `1 − levenshtein / max(len)` of the stripped texts has median ≥ 0.98 and
  10th percentile ≥ 0.90 (nearest rank); the exact-match rate and line-count
  deltas are reported only. Changing a threshold is a spec change.

A fixture whose oracle output turns out to differ from ours is never
relabelled to make the gate pass; it is a finding for the spec.

## Corpus D (OCR quality)

Run spec 0002 §3.8 and Appendix C. Corpus D is 52 image-only pages with
known ground truth: the test kit's vector pages
(`crates/testkit/src/corpus_d/mod.rs`) rasterised in gray by the **oracle**,
so no scan comes from the renderer under test. Forty files are committed
in `tests/fixtures/corpus-d/` with a `<name>.txt` ground truth each: 12
clean pages, their skew and blur variants (Pillow), 3 pages scanned at
150 dpi and one JPEG page (22.3 MB). The 12 noise variants (σ 12) would
add 55 MB that does not compress, so the Rust test kit builds them at test
time from the committed clean files into `target/corpus-d/`, with integer
noise whose bytes are identical on every host; `manifest.toml` pins their
SHA-256s in `[[built]]` rows.

The gate is `crates/ocr/tests/quality.rs` (CI job `corpus-d`): ours at 72
dpi within one CER point of the oracle at 72 dpi, and ours at 300 dpi
better than both, over the per-subset means; latency and RSS are
report-only. It needs the pinned model, tessdata_fast `eng.traineddata`
(SHA-256 `7d4322bd…170b2`): every committed number belongs to that file.

```sh
cd tools/oracle
uv run python mkcorpusd.py --fetch-model       # model into .cache/tessdata_fast
cd ../..
TESSDATA_PREFIX=$PWD/tools/oracle/.cache/tessdata_fast \
    cargo test --release -p pdf-extract-ocr --test quality -- --include-ignored --nocapture
```

After changing a recipe, the noise model or the noise assembly (in this
order; each step reads what the previous one wrote):

```sh
cd tools/oracle
uv run python mkcorpusd.py                     # the 40 committed files, manifest and PROVENANCE rows
cargo run -p pdf-extract-testkit --example corpus_d_noise -- ../../target/corpus-d
uv run python mkcorpusd.py --pin-built ../../target/corpus-d
uv run python gen.py --ocr --tessdata .cache/tessdata_fast \
    --built ../../target/corpus-d ../../tests/fixtures/corpus-d
uv run python mkcorpusd.py --verify --compare-pixels --built ../../target/corpus-d
```

MuPDF randomises the file identifier on save, so regenerated files have
new hashes (but the same pixels, which `--compare-pixels` proves);
regenerating the committed files alone leaves the noise pins valid, since
the variants depend on the clean files' pixels, not their bytes. `gen.py
--built` refuses to run when a built file differs from its pin, and both
`crates/testkit/tests/corpus_d_noise.rs` and `quality.rs` fail on a pin
mismatch, so a committed expectation always describes the bytes a test
scores. Run `gen.py --ocr` on corpus D only: without `--ocr` it would write
schema-1 expectations without the OCR block.

## Private scans (OCR)

```sh
tools/oracle/run_private_scans.sh <scans-dir> [<out-dir>]
```

The OCR counterpart of corpus A. Real scans have no ground truth, so it
measures agreement: the oracle's 72-dpi OCR of every PDF under
`<scans-dir>` (`gen.py --ocr` into `<out-dir>/expectations`, default
`${XDG_CACHE_HOME:-~/.cache}/pdf-extract-private-scans/<dir name>`) against
ours at 72 and at 300 dpi (the ignored `private::private_scans` test of
`quality.rs`, in release, with the same pinned model), reporting the median
and 10th-percentile character similarity and the routing agreement at
`min_chars = 50` (whether both sides would call the page sparse after OCR).
The numbers are report-only in this run. The same privacy rules as corpus A
apply: in-repository paths are refused and the report holds lengths,
similarities and flags, never text. Exit status 0 when every page was
scored, 1 when one could not be, 2 on a usage error.

## Private corpus (corpus A)

```sh
tools/oracle/run_private_corpus.sh <corpus-dir> [<out-dir>]
```

Runs the oracle over every file under `<corpus-dir>` (recursively, dotfiles
skipped), writing the expectations to `<out-dir>/expectations` (default
`${XDG_CACHE_HOME:-~/.cache}/pdf-extract-private/<corpus name>`), then runs
the ignored `gate_a_private` test of `parity.rs` in release with the
corpus-A gates of design spec §13.2: 100% of the files the oracle opens open,
routing agreement ≥ 99.9%, similarity median ≥ 0.999 and 1st percentile
≥ 0.98, with the same metric definitions as gate B. It prints the report
(`score.py --gate-report`) and leaves `report.json` and `cargo.log` in
`<out-dir>`; the exit status is 0 if every gate passes, 1 if one fails, 2 on
a usage error.

The corpus may be confidential: the script refuses a corpus or output
directory inside the repository, the report holds lengths and similarities
but no page text, and nothing it writes is meant to be committed. It needs
this uv project (PyMuPDF) and is never run on CI. A rerun regenerates every
expectation and prunes those of removed files.

## Python interpreter

On Apple-silicon machines uv may pick an x86_64 (Rosetta) interpreter; give it
an arm64 one explicitly, e.g.
`UV_PYTHON=$(uv python find 3.13) uv sync` after checking the architecture,
or point `UV_PROJECT_ENVIRONMENT` at a scratch venv built from an arm64
CPython. The oracle's output does not depend on the architecture.

## measure_tessdata.sh

`measure_tessdata.sh` scores `tessdata_fast`, `tessdata_best` and the combined
`tessdata` set on corpus D (blob and SHA-256 pins inside the script) and
rewrites the table in `docs/reference/tessdata-measurement.md`. It drives
`quality.rs` in report-only mode through `PDF_EXTRACT_TESSDATA=<dir>`, which
skips the model pin and the gates and writes `target/ocr-report-measure.json`.
Takes about 8 minutes; use `--no-write` to print the table instead.
